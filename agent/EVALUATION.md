# 异质模型 × Harness 评估与归因

## 1. 评估问题

不是寻找最高自评分，而是回答：弱模型为何漏生图/混字体/用色条/丢语义；是规范互相冲突、模型未读到、不会执行、工具失败，还是渲染器不支持？生成可用性、视觉质量、信息忠实度、交互正确性、成本和时间分开记录。

## 2. 模型选择与公平条件

探测当时可用的至少三个能力档：L（低成本/小上下文或小模型）、M（中档）、H（高能力），至少两家模型家族。档位是本次任务上的经验分类，不凭品牌排名。每个模型固定确切版本、temperature/seed（支持时）、最大输出、context、工具可见性、vision能力。先记录事实，不虚构“已连接”。

VLM 另选两档，尽量不同家族；评审不知道生成模型与 harness，不看生成者自评。至少一位评审没有参与生成。评审分歧进入仲裁，**不要求所有视觉事实必须双模型一致才能前进**；高风险语义与不确定视觉问题保留人工决定。

同一任务的材料、品牌 token、目标轨道、允许工具权限相同。统计累计输入/输出token、工具成本、修复次数和端到端时间；warm-up 单列。时间/预算不足应停止并说明，而不是偷换便宜任务。

## 3. Harness

H0 单次长上下文基线：相同有效规则展开成一个提示，不含旧版冲突；一次生成后评审，不自动修。

H1 路由式：入口+共同硬约束+目标轨道+条件模块，先页面计划再生成。与 H0 保持规则内容等价，研究分层加载的影响。

H2 结构化执行：在 H1 上加 page/film/image sidecar、前后 QC、可执行断言与最多两次局部修复。它消耗更多步骤，必须把额外成本计入，不能宣称仅靠“规范文本更好”产生收益。

并非所有差异都能单独归于 harness：若 H2 用更强模型、更多图片调用或更长预算，须标记混杂。需要归因时做配对重跑，限制模型、预算和工具相同。

## 4. 样本设计

先使用 `fixtures/cases.json` 中标为 pilot 的3个案例；两种生成模型×H1/H2×3案例，共12次。低风险每例单次只用于查错，不给统计显著性结论。

关键失败在两个模型或同模型至少两次复现后，再归因为稳定模式；能用代码/输入证明的确定性缺陷不必额外花模型成本。进入验证阶段后，选三档模型×H0/H1/H2×四个代表案例（36次），按资源预算决定；只有用户同意的预算/连接下运行。

至少保留三分之一案例不用于规范修订。fixture 可以故意高密度、含中英缩写/数字范围/缺失值/内部怪文件名，检验真正边界；不能都用三张大卡的容易样本。持出集结果失败时不得把它改成训练案例后仍称持出通过。

## 5. 门与评分

先过机器门（结构、字号、色条嫌疑、数据一致、交互、资产回执）；出现严重事实改变、整页栅格化、未生图冒充生图等硬失败直接 FAIL，不让漂亮外观抵消。

机器门不是完整视觉门。VLM 必须看原始材料摘要、对应页大图、局部裁图、图像保护叠图；电影须看关键帧和正常速度视频（不支持视频的 VLM 则关键帧+人工动态复核，明确限制）。不得仅看HTML源码。

分维度0–4：品牌与材料、空间/字体、中文质量、数据和语义、图文配合、叙事与动态、交互与可编辑、跨轨一致。缺失维度为 NOT_TESTED，不记0也不记满分；总分只对已适用维度计算，附覆盖率。0–1需返工、2需局部修订、3可用、4良好。硬门优先于均值；阈值只是本项目验收规则，不是通用科学量表。

## 6. 归因标签与证据

| 标签 | 需要的证据 | 典型干预 |
|---|---|---|
| SPEC_CONFLICT | 两条有效规则直接矛盾，或 schema 与正文冲突 | 单一 owner 合并规则，删除旧例外 |
| SPEC_GAP | 明确需求在可见规范中缺少可执行边界 | 增加最小正反例/默认值/验收，而非继续堆提示 |
| HARNESS_ACCESS | 规范存在但未被加载，或工具不可见/中途摘要丢失 | 改路由、检索和上下文保留 |
| MODEL_LIMIT | 已加载明确规则；同工具/预算下，多次仍不能完成，而更强模型稳定完成 | 换模型或减小单次任务；不能降低品牌要求 |
| IMPLEMENTATION | 固定输入可由代码复现，模型无关 | 修组件、转换或计算 |
| ENVIRONMENT | 字体、浏览器策略、Office特性、provider连接不可用 | 记录环境并在目标环境复测 |
| JUDGE_ERROR | 评审漏读/误判可由材料或确定性检查反证 | 调整评审提示/仲裁，不盲信 VLM |
| MIXED_UNKNOWN | 证据不足或混杂无法区分 | 标记待辨别，设计最小配对试验 |

禁止“弱模型失败一次 → 模型能力问题”；也禁止“更强模型偶尔成功 → 规范已无问题”。不要仅靠失败者自己的解释做归因。

## 7. 有界循环

一个循环：冻结基线 → 生成 → 机器检查 → 盲审 → 证据聚类 → 最小干预 → 同样例复跑 → 保留集回归。每个执行批次最多3轮或到该批预算上限后重新评估；每轮有独立 handoff。用户已授权持续推进时，批次结束不等于全任务停止：据失败证据调整方法，冻结下一批合同再继续。只有完成标准通过、用户停止、必要权限缺失或安全替代耗尽时停止。

优先顺序：先事实/可编辑/工具真实调用，再重叠字号/原生行为，再光学细节/叙事流畅。不得为提分改掉测试数据、放松下限、把复杂图换简单图、给所有页重复强调句或删除必要信息。

## 8. 输出

每次 `run.json` 至少包含：case_id、model_id/version/provider、harness_id、spec_hash、upstream_sha、input_hash、output_hash、seed、token_budget、tool_caps、tool_receipts、timestamps、cold_start_ms、generation_ms、qc_ms、cost_known/unknown、screenshots/video、deterministic_findings、blind_judge_reports、attribution/confidence/evidence、repairs、final_status。

任何 coordinator 后期改动都另记 repair，不覆盖原始生成物。保留失败的原件及其记录；资料含敏感信息时只存授权位置，对外交付索引与脱敏证据，不把临床原件打包进公共skill。

## 9. 四轨独立多轮验收（A04）
四行分别是 PPTX、HTML-PPT、站点式 HTML、流式 HTML；每行至少记录生成、盲审、修订和同输入复测两轮，不能用总运行次数代替轨道覆盖。最终冻结包须连续两轮完整回归无新增缺陷，已知硬失败清零，并包含未参与修订的保留集。失败的保留集一旦用于修订，移入开发集并补充未见案例。

每行记录模型和真实 harness、确切输入/规范/产物哈希、预算和工具、上游调用回执、独立审阅、修复归属和终态。PPTX 制作者本人须跑完 ppt-master Default；HTML-PPT 制作者本人须完成 html-ppt-skill 脚手架、唯一导航/演讲者、导出全链。站点与流式分别核对各首屏正常速度电影、宽屏和多层下钻。组件测试、协调者成品、Office编辑检查分别计数，不替代测试者生成通过。缺失/失败节点不算完整一轮。
